# Полное описание логики каскада
1. Основные роли и сущности
В каскаде участвуют три стороны:
1. Мерчант
2. Наш сервис
3. Провайдер
Мерчант создает у нас сделку. Мы либо обрабатываем эту сделку сами, либо передаем ее дальше по каскаду следующему сервису / провайдеру.
При этом мерчантом может выступать такой же сервис, как наш: он передал сделку нам по каскаду, а мы можем передать ее дальше другому аналогичному сервису.

⸻

2. Важное уточнение по терминологии
В проекте есть путаница между:
* merchant как модель / магазин 
* merchant как роль пользователя
То же самое есть с provider:
* provider как роль пользователя ( liquidity provider.)
* Cascade Provider как сущность / модель провайдера в каскаде
В этом документе, если не указано иное:
* под мерчантом имеется в виду магазин / merchant model;
* под провайдером имеется в виду Cascade Provider, то есть сущность каскадного провайдера;
* роли пользователей мерчанта и провайдера будут описываться отдельно.

⸻

3. Виды провайдеров
В каскаде есть два вида провайдеров:
3.1. Внутренний провайдер
Внутренний провайдер — это наша собственная ликвидность.
Фактически это текущая внутренняя логика с трейдерами, которые обрабатывают заявки.
3.2. Внешний провайдер
Внешний провайдер — это внешний сервис, которому мы передаем сделку по API.
У него уже свои трейдеры, своя логика обработки, свои комиссии и свои обязательства перед трейдерами.

⸻

4. Финансовые обязательства
4.1. Обязательства перед мерчантом
Мерчант создает сделку в фиатной валюте.
Он ожидает получить от нас сумму в USDT за вычетом комиссии.
Сумма конвертируется из фиата в USDT по определенному курсу.
Курс может быть:
* внутренним курсом нашего сервиса, который парсится из market-сервиса;
* курсом, который сам мерчант передает нам при создании сделки.
После конвертации мы рассчитываем:
* общую сумму в USDT;
* комиссию;
* сумму, которую должны зачислить мерчанту.

⸻

4.2. Внутренний провайдер
При работе с внутренним провайдером сделку обрабатывают наши трейдеры.
Мы списываем средства с кошелька трейдера и распределяем прибыль:
* часть комиссии остается сервису;
* часть уходит трейдеру;
* также может быть логика, связанная с тимлидером.
Важно: внутренняя логика уже существует и работает через host-to-host API / merchant API. Ее нельзя ломать или менять в рамках реализации каскада.

⸻

4.3. Внешний провайдер
При работе с внешним провайдером трейдеры находятся на стороне внешнего сервиса.
Мы передаем сделку внешнему провайдеру по API. Он у себя:
* конвертирует сумму;
* применяет свой курс;
* применяет свои комиссии;
* возвращает нам сумму в USDT, которую он должен нам зачислить.
Для нас не важно, как именно внешний провайдер рассчитывает свои комиссии и курс.
Для нас важно только одно:
сумма, которую мы получаем от провайдера, должна быть больше или равна сумме, которую мы отдаем мерчанту.
Иначе сделку нельзя принимать.

⸻

4.4. Пример финансовой логики
Мерчант создал сделку.
Мы рассчитали:
* total: 100 USDT;
* комиссия: 5 USDT;
* сумма к выплате мерчанту: 95 USDT.
Далее мы создаем сделку у внешнего провайдера.
Внешний провайдер рассчитывает свою сумму. Не важно, какой у него курс и комиссия.
Важно, чтобы он вернул нам минимум 95 USDT или больше.
То есть мы должны работать:
* либо в ноль;
* либо в плюс.

⸻

5. Баланс внешнего провайдера
Для внешнего провайдера должен быть отдельный аккаунт и отдельный кошелек.
Этот кошелек фактически является залогом / trust-балансом.
Провайдер реально пополняет баланс, например на 4000 USDT.
Когда мы создаем сделки у этого провайдера, мы списываем средства с его баланса.
- Важное замечание: при создании новой роли провайдера ликвидности мы должны в модели Wallet создать ему новый баланс, нельзя использовать баланс, который у трейдера или мерчанта.
5.1. Что именно списывать
Есть важное уточнение.
Списывать нужно не только сумму, которую мы должны получить как выплату, а сумму наших обязательств перед мерчантом.
Например:
* мерчант создал сделку;
* после конвертации получилось 100 USDT;
* мерчанту после комиссии мы должны отдать 95 USDT.
Но обязательство перед мерчантом — это 100 USDT.
Значит, с баланса внешнего провайдера нужно списывать 100 USDT.
Это залоговая логика.

⸻

5.2. Неясность по сведению баланса
Есть нерешенный вопрос: как правильно сводить баланс после успешного закрытия сделки и фактического получения выплаты от внешнего провайдера.
Пример:
* провайдер пополнил залог на 4000 USDT;
* мы обрабатывали сделки;
* списали с его залога 4000 USDT;
* фактически он выплатил нам 3000 USDT; (Примечание: меньше 4000 потому что списывали у него 100, а получали 95,  разница в обязательствах перед мерчантом и провайдером)
* после подтверждения выплаты нужно понять, как делать сверку и восстановление залогового баланса.
Возможная логика:
* мы заранее фиксируем ожидаемую сумму выплаты от провайдера;
* после фактического получения выплаты подтверждаем ее;
* после сверки возвращаем провайдеру соответствующую сумму залога;
* он снова может продолжать работу.
Этот блок требует отдельного проектирования.

⸻

6. Общая цепочка создания сделки
6.1. Создание сделки мерчантом
Мерчант обращается к нам по Cascade API и передает:
* сумму;
* валюту;
* тип сделки, например card;
* другие необходимые параметры.
Мы валидируем запрос.
Если все корректно, запускается каскадная логика.
 - примечание важное. В данный момент в проекте реализованы вот эти интерфейсы, они являются окончательными и верными. App\Http\Requests\API\V2\Order\StoreRequest
App\Http\Requests\API\H2H\Order\StoreConfirmationCodeRequest
App\Http\Requests\API\V2\Dispute\StoreRequest
 - второ важное примечание. В Каскаде не будет отмены спора, как это сделано в хост to host API. Эта логика и линия должна быть отменена и вырезана в каскаде. То есть сам мерчант с запросом по API не может  отменить спор если он его открыл, если спор открыт, то трейдер теперь должен его обработать, или внешний провайдер. 
Под соответствующий request interface App\Http\Requests\API\V2\Dispute\CancelRequest

⸻

6.2. Запуск провайдеров
Каскад запускает джобы на создание сделки у провайдеров:
* у внутреннего провайдера;
* у внешних провайдеров.
Работает race-механика:
кто первый успешно создал и привязал сделку к CascadeDeal, тот и выиграл.

⸻

6.3. Атомарная привязка сделки
Привязка сделки к CascadeDeal должна быть атомарной.
Нужно использовать lock для CascadeDeal.
Если провайдер создал сделку и пытается привязать ее к CascadeDeal, но там уже есть другая выбранная сделка:
* текущая сделка не должна перезаписывать существующую;
* нужно отправить запрос на отмену созданной сделки;
* это касается и внутренних, и внешних провайдеров.

⸻

6.4. Отмена проигравших попыток
Все jobs, которые не успели создать сделку, должны получить сигнал, что сделку создавать уже не нужно.
Если сделка уже была создана, но не выиграла race, она должна быть отменена. (создается job на отмену сделки)
Гарантированно не должно быть ситуации, когда создано несколько сделок и часть из них не отменена.

⸻

7. Внутренний провайдер
7.1. Общий принцип
Внутренний провайдер нужно воспринимать как внешний сервис, но с отдельными исключениями.
Каскад должен общаться с внутренним провайдером через адаптер / интерфейс, как будто это внешний провайдер.
При этом нельзя ломать существующую host-to-host / merchant API-логику.

⸻

7.2. Расчеты внутреннего провайдера
Для внутреннего провайдера нельзя заранее предопределять финансовые поля.
Внутренний провайдер сам должен рассчитать:
'debit',
'credit',
'service_profit',

'usdt_amount',
'fee',
'fee_rate',

'market',
'conversion_price',
'rate_fixed_at',
Также могут быть другие поля, которые зависят от внутреннего провайдера.
После создания сделки мы копируем точные значения из внутренней сделки в CascadeDeal.
Важно сохранить точность до 8 знаков после запятой. (как это в модели Order)

⸻

7.3. Почему нельзя рассчитывать заранее
Внутренний провайдер должен работать так, как будто сделка была создана через старую host-to-host API-логику.
То есть Cascade должен только имитировать обращение к внутреннему провайдеру, а не вмешиваться в его расчеты.
После успешного создания сделки Cascade может получить данные напрямую из модели сделки и записать их к себе.

⸻

7.4. Обновления статуса
Когда у сделки внутреннего провайдера меняется статус, это изменение должно передаваться в CascadeDeal через единый интерфейс.
Такая же логика должна быть и для внешних провайдеров.
Желательно, чтобы изменения от внутреннего провайдера приходили в Cascade как псевдо-callback.
пвсевдо Callback - это такой же вызов калбэка во внутреннем провайдере, только мы не обращаемся по HTTP к какому-то API, а можем вызвать какой-то метод в каскаде, который реализует обработку колбеков и передать данные будто бы это запрос от внешнего провайдера. (Хотя как правильно реализовать я это не знаю.) Но очень важно, чтобы изменения из внутреннего провайдера приходили в каскад точно так же через калбеки.
⸻

7.5. Manual Control Acquiring
Manual Control Acquiring также должен работать через симуляцию host-to-host API.
Для внутреннего провайдера Cascade должен выглядеть как внешний сервис.
При этом при изменениях должны обновляться поля CascadeDeal и отправляться каскадные callbacks.
То есть каскад должен поддерживать Manual Control Acquiring. Данный момент поддержка реализована не полностью.

⸻

7.6. Споры во внутреннем провайдере
Во внутреннем провайдере сейчас можно создавать только один чек.
В каскадном интерфейсе можно передавать до трех чеков.
Временная логика:
* для внутреннего провайдера берем первый чек из списка;
* отправляем только его;
* в CascadeDeal сохраняем все чеки и всю историю спора.
Для внешнего провайдера отправляем столько чеков, сколько позволяет его API.

⸻

7.7. Ограничение
Нельзя менять существующую логику внутреннего провайдера так, чтобы это сломало:
* host-to-host API;
* merchant API;
* текущие интеграции.
Cascade должен быть реализован поверх существующей логики.

⸻

8. Внешний провайдер
8.1. Аккаунт провайдера ликвидности
В проекте нужно создать новую роль:
Provider Liquidity / Провайдер ликвидности.
У него должна быть своя панель.

⸻

8.2. Страницы провайдера ликвидности
У провайдера ликвидности должны быть:
Главная страница
С общей информацией и статистикой в его контексте.
Страница сервисов / интеграций
Провайдер видит список сервисов, с которыми мы интегрированы.
Он не может:
* добавлять сервисы;
* редактировать сервисы.
Он может видеть только нечувствительную информацию:
* название;
* дату создания;
* другие безопасные данные.
Страница сделок
Провайдер видит свои каскадные сделки.
Нельзя показывать чувствительную информацию, например сколько мы на нем зарабатываем.
Страница кошелька
Провайдер видит:
* баланс;
* транзакции по кошельку.
Пополнения и вывода у него нет.
Администратор может:
* зачислять средства;
* списывать средства.
Страница логов
Провайдер видит API-логи только по своим запросам:
* что мы отправили;
* что получили;
* какой был ответ;
* какие ошибки возникли.

⸻

8.3. API внешнего провайдера
Интерфейс внешнего провайдера может быть похож на наш.
Ожидаемые методы:
* создание сделки;
* просмотр сделки;
* отмена сделки;
* создание спора;
* callbacks;
* другие методы, если они уже описаны в интерфейсах провайдеров.
Каждый внешний провайдер может иметь свой API, поэтому для каждого нужен адаптер к нашему универсальному каскадному интерфейсу.

Каскад является универсальным интерфейсом и прослойкой между мерчантом и внутренним, внешними провайдерами 
⸻

8.4. Финансовая проверка внешнего провайдера
При создании сделки у внешнего провайдера мы должны:
1. Рассчитать обязательства перед мерчантом через существующий profit-service.
2. Создать сделку у внешнего провайдера.
3. Получить от него сумму в USDT, которую он должен нам выплатить.
4. Проверить, что эта сумма больше или равна сумме, которую мы должны отдать мерчанту.
Если условие не выполняется — сделка должна быть отменена.

⸻

8.5. Момент списания баланса
Сделка считается созданной только тогда, когда она успешно привязана к CascadeDeal.
Не когда успешна попытка создания, а именно когда попытка выиграла race и была привязана.
Только после этого нужно списывать баланс внешнего провайдера.

⸻

9. CascadeDeal как главная сущность
CascadeDeal — это основная верхнеуровневая сущность.
Все, что происходит с внутренним или внешним провайдером, должно отражаться в CascadeDeal.
Нужно сохранять:
* статусы;
* историю изменения статусов;
* споры;
* чеки;
* изменения суммы;
* manual acquiring-информацию;
* callbacks;
* всю доступную историю.
* Мы ведем и сохраняем всю историю ведения изменения данных, а также мы у админа есть возможность ее просматривать. Очень компактно, удобно, аккуратно, адаптивно.
Нельзя терять информацию, даже если она пришла от внутреннего или внешнего провайдера.

⸻

10. Споры
10.1. Отдельной модели спора в каскаде не нужно
Для Cascade не создаем отдельную модель Dispute, как у внутреннего провайдера.
Вся информация по спору должна прикрепляться к CascadeDeal.

⸻

10.2. Статусы спора
У каскадного спора должно быть три статуса:
* opened
* accepted
* rejected

⸻

10.3. История спора
По CascadeDeal нужно хранить:
* факт открытия спора;
* статус спора;
* причину;
* все чеки;
* изменения статуса;
* историю решений.

⸻

10.4. Интерфейс спора
При создании спора и получении информации по спору должен возвращаться такой интерфейс в API: 
return [
    'payin_id' => $this->order->uuid,
    'status' => $this->status->value,
    'reason' => $this->reason,
    'canceled_at' => $this->canceled_at,
];

⸻

11. Callbacks
11.1. Callbacks мерчанту
Нужно реализовать отдельную линию callbacks по каскадным сделкам.
Callbacks должны отправляться мерчанту при изменениях CascadeDeal.

⸻

11.2. Callbacks от внешнего провайдера
От внешнего провайдера мы получаем callbacks:
* по сделкам;
* по спорам;
* по изменениям статуса;
* по manual acquiring;
* по изменению суммы.
У каждого провайдера обработчик может быть уникальным, но результат должен приводиться к единому каскадному интерфейсу.

⸻

11.3. Callbacks от внутреннего провайдера
Изменения внутреннего провайдера желательно передавать в Cascade через псевдо-callback.
Идея:
* внутренняя логика продолжает работать как раньше;
* если сделка относится к Cascade, вместо внешнего callback запускается обращение к Cascade;
* Cascade обновляет CascadeDeal;
* Cascade отправляет свой callback мерчанту.

⸻

11.4. Единый ресурс ответа
Файл:
App\Http\Resources\API\V2\OrderResource
сейчас содержит описание интерфейса.
Этот ресурс должен использоваться:
* при создании каскадной сделки;
* при ответах API;
* при отправке callbacks.
Часть полей пока не реализована в CascadeDeal, их нужно реализовать.

⸻

12. Статусы CascadeDeal
Сейчас в CascadeDeal ошибочно используются enum от обычных сделок внутреннего провайдера:
App\Enums\OrderStatus
App\Enums\OrderSubStatus
Для каскада нужно создать свои enum.

⸻

12.1. OrderStatus
Для каскада OrderStatus в целом может быть таким же, всего три статуса.

⸻

12.2. OrderSubStatus
Для каскада нужны такие sub-status:
case SUCCESSFULLY_PAID = 'successfully_paid'; 
// закрыт с успехом

case WAITING_FOR_PAYMENT = 'waiting_for_payment';
// ждет платежа

case CANCELED = 'cancelled';
// закрыт с неуспехом

case SUCCESSFULLY_PAID_BY_RESOLVED_DISPUTE = 'successfully_paid_by_resolved_dispute';
// принят в результате спора

case WAITING_FOR_DISPUTE_TO_BE_RESOLVED = 'waiting_for_dispute_to_be_resolved';
// ожидает решения спора

case CANCELED_BY_DISPUTE = 'canceled_by_dispute';
// отклонен в результате спора
Эти статусы нужно поддерживать и для внутреннего, и для внешнего провайдера через маппинг.

⸻

12.3. История статусов
По CascadeDeal нужна история изменения статусов:
* кто изменил;
* с какого статуса;
* на какой статус;
* когда изменил.

⸻

13. Изменение суммы сделки
13.1. Внутренний провайдер
Во внутреннем провайдере трейдер может изменить сумму сделки в фиате.
После этого пересчитывается USDT-сумма, списания, зачисления и комиссии.
Если такое произошло, Cascade должен получить точные обновленные значения и записать их в CascadeDeal.

⸻

13.2. Внешний провайдер
Внешний провайдер тоже может прислать другую сумму.
В CascadeDeal должны быть поля:
* initial_amount — сумма при создании;
* amount — текущая сумма, которая может изменяться.
При изменении суммы нужно:
* записывать историю изменения;
* пересчитывать USDT;
* обновлять обязательства перед мерчантом;
* обновлять списания / зачисления по провайдеру;
* отправлять callback.

⸻

14. Очереди, асинхронность и тайм-ауты
14.1. Все внешние обращения только через очереди
Через очереди должны работать:
* запросы к внешним провайдерам;
* callbacks мерчанту;
* callbacks / запросы во внешние API;
* отмены сделок;
* обработка race-логики.
Нельзя выполнять синхронные обращения к чужому API.

⸻

14.2. Horizon
В Horizon для каскадной очереди нужно расширить количество потоков до 8.

⸻

14.3. Глобальный тайм-аут
Обязательный тайм-аут очереди — 10 секунд.
Если за 10 секунд задача не завершилась, нужно:
* завершить задачу с ошибкой;
* записать лог;
* указать, что произошел timeout;
* сохранить контекст: провайдер, сделка, спор или другой объект.
* Когда я говорю про лог, я имею в виду тот лог, который находится у админа на странице логи каскада.

⸻

14.4. Тайм-аут провайдера
У провайдера в настройках администратора должен быть свой timeout.
Он:
* обязателен для всех провайдеров;
* не может быть больше 10 секунд;
* может быть меньше 10 секунд.
Например, если указано 3 секунды, мы ждем ответ только 3 секунды.
Если за 3 секунды провайдер не успел создать сделку, попытка завершается ошибкой по timeout.

⸻

14.5. Timeout у внутреннего провайдера
Может быть ситуация:
* Cascade завершил попытку создания сделки по timeout;
* но внутренний провайдер все-таки создал сделку.
Эту ситуацию нужно обрабатывать на стороне Cascade, не меняя внутренний провайдер.
Предлагаемая логика:
* Cascade хранит неуспешные попытки создания внутренней сделки;
* если по попытке был timeout, специальный cron проверяет, появилась ли сделка во внутренней модели Order;
* важное упоминание, что он сначала проверяет, существует ли у нас Coscate Transaction, которая была завершена тайм-аутом во внутреннем провайдере.
* А потом он уже ищет сделку соответствующую модели Order.
* проверка идет по merchant / external_id / другим идентификаторам;
* если сделка найдена, но не привязана к CascadeDeal, ее нужно принудительно закрыть.
Эта логика должна работать:
* через scheduler / cron;
* примерно раз в 10 секунд;
* через отдельную однопоточную очередь Horizon.
* Это такая логика, как бы она со стороны находится, чтобы сохранять консистентность. Чтобы мы реквизиты по пусту не занимали. Сделками, которые никогда не будут обработаны.

⸻

14.6. Timeout у внешнего провайдера
Если внешний провайдер не успел ответить, а потом создал сделку у себя, это его проблема.
У нас:
* фиксируется timeout;
* пишется лог;
* попытка считается неуспешной.

⸻

15. Manual Acquiring
В CascadeDeal нужно реализовать поля и логику для manual acquiring.
Должны обрабатываться:
* confirmation_type;
* reject_reason;
Эта информация может приходить как от внутреннего, так и от внешнего провайдера.

⸻

16. PayIn / PayOut
Сейчас Cascade реализует линию, которая называется order, но в интерфейсе роутов предоставляется как PayIn.
Это одно и то же.
В будущем будут выплаты — PayOut.
Сейчас PayOut не трогаем.

⸻

17. Валюта сделки
Сделку у внутреннего и внешнего провайдера нужно открывать в той же валюте, в которой мерчант открыл каскадную сделку.

⸻

18. Минимальная прибыль при каскадировании
Возможно, мы не захотим работать в ноль при передаче сделки внешнему провайдеру.
Нужна настройка процента минимальной прибыли.
Пример:
* обязательство перед мерчантом: 95 USDT;
* минимальная прибыль: 1%;
* значит, от внешнего провайдера мы хотим получить минимум 95 + 1%.
Сравнивать нужно не просто с 95, а с 95 плюс заданный процент.

⸻

19. Настройки провайдеров
19.1. Вес и приоритет
Сейчас у провайдеров есть:
* weight;
* priority.
Weight пока непонятно как использовать. Его можно убрать.
Priority нужно оставить.
Priority влияет только на порядок запуска джоб.

⸻

19.2. Общие настройки провайдера
Для каждого провайдера нужны общие настройки:
* включен / выключен;
* priority;
* timeout;
* минимальный процент прибыли;
* другие настройки интеграции.

⸻

19.3. Индивидуальные настройки мерчанта
Для каждого мерчанта нужно уметь:
* включить или выключить каскадирование его трафика;
* выбрать, какие провайдеры доступны для его сделок;
* отключить конкретных провайдеров;
* настроить, отправлять ли его сделки во внутреннего провайдера;
* настроить, отправлять ли его сделки во внешних провайдеров.
Есть сценарий, когда мы можем захотеть не отправлять ручные сделки мерчанта во внутреннего провайдера, а отправлять только во внешние.

⸻

20. Главный архитектурный принцип
Cascade должен быть верхнеуровневой абстракцией.
Он предоставляет мерчантам единый интерфейс.
Дальше он может:
* обработать сделку через внутреннего провайдера;
* передать сделку внешнему провайдеру;
* адаптировать разные API к одному универсальному интерфейсу.
Внутренний провайдер должен быть подключен к Cascade через адаптер и восприниматься почти так же, как внешний провайдер.
Исключения для внутреннего провайдера:
* получение точных расчетных значений после создания сделки;
* получение точных значений после изменения суммы;
* возможный псевдо-callback внутрь Cascade.

⸻

21. Важные требования надежности
1. Все операции с деньгами должны быть атомарными.
2. Все операции выбора победившей сделки должны быть атомарными.
3. Нельзя перезаписывать уже выбранного провайдера в CascadeDeal.
4. Все проигравшие созданные сделки должны отменяться.
5. Все обращения к внешним API должны идти через очереди.
6. Все timeout-ошибки должны логироваться.
7. Cascade не должен ломать существующие host-to-host API и merchant API.
8. CascadeDeal должен хранить полную историю по сделке, спорам, статусам, чекам и изменениям суммы.
