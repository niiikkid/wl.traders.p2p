# Payment Detail Work Schedule Requirements

> Source: User conversation in Cursor
> Collected: 2026-05-22
> Published: Unknown

## Original Request

ТЗ: Расписание работы реквизитов

### 1. Цель

Добавить возможность настраивать расписание работы реквизитов, чтобы реквизит принимал заявки только в заданные дни и временные интервалы.

Функция нужна для банков и реквизитов, которые нежелательно использовать в определённое время суток.

### 2. Основная логика

Пользователь может включить для реквизита работу по расписанию.

Если расписание включено, реквизит работает только в заданные дни и временные интервалы.

Примеры интервалов:

- с 09:00 до 19:00;
- с 00:00 до 23:59.

Вне заданного расписания реквизит не принимает заявки.

Статус реквизита включен/выключен не должен автоматически переключаться по расписанию.

Пользователь сам управляет статусом реквизита.

Если реквизит выключен вручную, расписание не должно включать его автоматически.

Если реквизит включен вручную, трафик на него попадает только с учётом расписания.

### 3. Условия работы

Если пользователь не включил онлайн-режим, трафик ему в любом случае не попадает.

Если пользователь онлайн, трафик попадает на реквизит только при выполнении условий:

- реквизит включен;
- расписание реквизита активно;
- текущее время входит в рабочий интервал.

### 4. Настройка расписания для реквизита

Расписание настраивается для конкретного реквизита.

В настройках реквизита нужно добавить блок «Рабочее расписание».

В блоке должны быть доступны:

- включение/выключение расписания;
- выбор рабочих дней недели;
- выбор общего времени начала работы;
- выбор общего времени окончания работы;
- возможность добавить отдельные интервалы для конкретных дней;
- удаление добавленных интервалов.

### 5. Описание UI расписания

В интерфейсе расписания отображается отдельный блок настройки режима работы реквизита.

Вверху блока находится переключатель «Расписание включено».

Если переключатель активен, реквизит работает по заданным правилам расписания.

Также отображается текущий статус по расписанию:

- Работает — если сейчас реквизит находится в рабочем интервале;
- Выходной — если сегодня реквизит не должен работать;
- Скоро начнёт работу — если сегодня рабочий день, но рабочий интервал ещё не начался;
- Рабочее время закончилось — если сегодня рабочий день, но рабочий интервал уже завершён.

Внутри блока отображается режим работы:

- рабочие дни недели;
- время начала работы;
- время окончания работы;
- дополнительные интервалы по отдельным дням, если они настроены.

Рабочие дни визуально выделяются синим цветом.

Выходные дни визуально отображаются серым/белым цветом.

### 6. Таблица реквизитов

В таблицу реквизитов трейдера нужно добавить отдельную колонку с информацией о расписании.

Колонку желательно расположить рядом со статусом реквизита.

В колонке нужно отображать:

- текущее состояние по расписанию;
- название применённого расписания;
- сегодняшний рабочий интервал, если он есть.

Примеры отображения:

- Работает
  09:00–19:00
- Выходной
- Начнёт через 2 часа
  14:00–20:00
- Рабочее время закончилось

Если рабочий интервал на сегодня не задан, можно отображать прочерк.

### 7. Ограничения по интервалам

Расписание настраивается в рамках одних суток.

Интервалы с переходом на следующий день не поддерживаются.

Пример интервала, который не нужен:

- 22:00–06:00

Такую логику не реализовывать, чтобы не усложнять поведение системы.

### 8. Расписания как шаблоны

Нужно добавить возможность создавать и сохранять готовые расписания.

Расписание — это сохранённый набор правил, который можно применить к одному или нескольким реквизитам.

Расписание должно иметь название.

Примеры:

Расписание «День»

- Пн–Вс
- 09:00–19:00

Расписание «Полный день»

- Пн–Вс
- 00:00–23:59

Пользователь должен иметь возможность:

- создать расписание при создании или редактировании реквизита;
- сохранить расписание;
- выбрать готовое расписание из списка;
- применить готовое расписание к другому реквизиту;
- отредактировать сохранённое расписание;
- видеть в таблице реквизитов, какое расписание применено.

### 9. Массовое редактирование

В существующий функционал массового редактирования реквизитов нужно добавить возможность применять расписание.

Пользователь должен иметь возможность выбрать готовое расписание и применить его сразу к нескольким реквизитам.

### 10. Ожидаемый результат

После реализации пользователь сможет:

- создавать расписания работы реквизитов;
- включать или выключать расписание для реквизита;
- выбирать рабочие дни недели;
- задавать рабочее время в рамках суток;
- добавлять отдельные интервалы для конкретных дней;
- сохранять расписания;
- применять готовые расписания к другим реквизитам;
- массово применять расписание к нескольким реквизитам;
- видеть в таблице реквизитов текущее состояние по расписанию;
- видеть название применённого расписания.

## Clarifications Accepted During Discussion

### Timezone and Time Display

Расписание считается по timezone сервера.

Настройка расписания тоже выполняется по времени сервера. Поля настройки должны показывать серверное время без скрытой конвертации, например `09:00-19:00 по времени сервера`.

На фронтенде можно дополнительно показывать понятные подсказки: какое сейчас время сервера и во сколько реквизит начнёт/закончит работу по времени пользователя. Важно, чтобы не было скрытой неточности и чтобы пользователю было очевидно, по какому времени задано расписание.

Абсолютные даты/моменты в проекте уже часто передаются как ISO (`toISOString()` / `toIso8601String()`), а браузер отображает их в timezone пользователя. Для расписаний важно не конвертировать сами правила `HH:mm`, а использовать ISO только для рассчитанных моментов статуса и подсказок.

### Schedule Entity Semantics

Расписание — полноценная отдельная сущность, которую можно прикрепить к одному или нескольким реквизитам.

Расписание не является одноразовой заготовкой. Если расписание отредактировать, изменения применяются ко всем реквизитам, к которым это расписание прикреплено.

Если нужно сделать отдельную версию расписания для одного реквизита, пользователь создаёт копию существующего расписания с новым названием, редактирует копию и применяет её к нужному реквизиту.

Расписание принадлежит трейдеру.

Название расписания уникально в рамках пользователя.

Удаление расписаний в первой версии не требуется. Расписание можно редактировать и переиспользовать, но не удалять.

### Enabling and Disabling Schedule for a Payment Detail

Флаг применения расписания находится у реквизита, а не у расписания.

Выключить расписание для реквизита значит убрать расписание у реквизита.

Нет глобального выключения самой сущности расписания.

В массовом редактировании должны быть два действия:

- применить выбранное расписание к выбранным реквизитам;
- убрать расписание у выбранных реквизитов.

Если расписание не выбрано у реквизита, реквизит работает как сейчас и расписание никак не влияет на подбор.

### Rules and Intervals

Общий интервал расписания применяется к выбранным рабочим дням.

Если для конкретного дня заданы отдельные интервалы, они заменяют общий интервал этого дня. Дневное правило старше общего правила в рамках одного расписания.

В один день можно задать несколько интервалов.

Пересечения интервалов в рамках одного расписания и одного дня запрещены.

Интервалы с переходом через полночь не поддерживаются.

Для границ интервала принимается правило: начало включительно, конец исключительно.

Активное расписание нельзя сохранять без настроенных рабочих дней и рабочих интервалов.

### Statuses

Если сейчас реквизит находится внутри интервала, статус `Работает`.

Если сегодня нет интервалов, статус `Выходной`.

Если сегодняшний первый или следующий интервал ещё впереди, статус может быть `Скоро начнёт работу` или более точный вариант `Перерыв до 15:00`, если день уже начался, один интервал закончился и следующий ещё впереди.

Если все сегодняшние интервалы закончились, статус `Рабочее время закончилось`.

Расчёт статуса в таблице можно делать на фронтенде по переданным правилам/рассчитанным данным и текущему времени.

### Access Rules

Трейдер создаёт, редактирует и применяет свои расписания.

Тимлиды и администраторы могут просматривать расписания реквизитов трейдера.

Администратор в первой версии не редактирует трейдерские расписания, чтобы не создавать риск неожиданных массовых изменений для реквизитов трейдера.

### UI Behavior

Должна быть отдельная модалка со всеми расписаниями трейдера: в ней можно создавать, редактировать и копировать расписания.

При создании или редактировании реквизита можно нажать «создать новое расписание». Открывается модалка создания расписания. После успешного создания модалка закрывается, новое расписание сразу появляется в списке и автоматически выбирается для текущего реквизита.

При редактировании расписания нужно предупреждать, что изменения применятся ко всем реквизитам, где используется это расписание.

### Existing `PaymentDetailEnabledPeriod`

Существующая сущность `payment_detail_enabled_periods` относится к статистике фактической включенности реквизита и не должна использоваться как расписание.

Новое расписание — отдельная вещь, которая участвует в подборе реквизитов.

### Selection and Active Counts

Логика расписаний должна применяться к подбору реквизита для заявок.

Та же логика должна применяться к “доступным картам” и местам, где считаются активные/доступные реквизиты, включая:

- админскую логику доступных карт;
- merchant-facing виджеты доступных карт на главной странице;
- счётчики активных реквизитов в интерфейсе.

Кэш активных реквизитов на 15 секунд можно оставить как есть; не требуется специально сбрасывать его при изменении расписаний.
